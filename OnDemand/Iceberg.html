Módulo 01 · Plataforma

¿Qué es un clúster y por dónde se entra?

  • Un clúster es un grupo de servidores (nodos) que trabajan como uno solo: los datos se reparten y cada nodo procesa su parte al mismo tiempo.
  • Hay nodos Master (coordinan) y nodos Worker (guardan datos y calculan).
  • No te conectas a todos: entras por un nodo de acceso llamado gateway (o edge node). Desde ahí abres Spark y envías tu trabajo al clúster.
  • Para consultar con SQL usas Hue (Cloudera Data Explorer) desde el navegador: no necesitas instalar nada.
Analogía
Un turno de mantenimiento: el jefe de turno (maestro) reparte órdenes y las cuadrillas (trabajadores) las ejecutan en paralelo. Tú entregas la orden en la portería (gateway).

Módulo 02 · Formatos

Una tabla son datos más metadatos

  • Una tabla organiza datos en filas (registros) y columnas (atributos). El esquema es la lista de columnas con su tipo: texto, número, fecha.
  • En la plataforma, una tabla tiene dos partes: los datos (archivos en HDFS) y los metadatos (su definición: columnas, formato, ubicación).
  • Parquet es el formato de archivo recomendado: guarda los datos por columnas, comprimidos y con su tipo. Un motor lee solo las columnas que necesita.
  • Una tabla grande se particiona: sus datos se separan por un valor (por ejemplo, el mes) para leer solo lo necesario.
Concepto
Las tablas se nombran base.tabla. En este laboratorio: ws_<tu_usuario>.kpi_planta.

Módulo 02 · Formatos

Lo que necesita una tabla moderna

Cuando una tabla es solo una carpeta con archivos Parquet, el motor debe listar la carpeta para saber qué contiene. Eso funciona, pero deja preguntas abiertas que Iceberg responde:

Necesidad Con una tabla basada en carpetas Con una tabla Iceberg
Escrituras seguras Un lector puede ver archivos a medio escribir. Cada cambio se publica completo o no se publica (commit atómico).
Cambiar columnas Renombrar o quitar columnas puede desalinear datos antiguos. Cada columna tiene un ID propio: el esquema evoluciona sin reescribir datos.
Particiones Hay que conocer las carpetas y filtrar por columnas técnicas. Particionamiento oculto: filtras por la columna de negocio.
Historia El estado anterior se pierde al sobrescribir. Snapshots: consultar o volver a una versión previa.
Actualizar y borrar filas Se reescribe la partición completa a mano. UPDATE, DELETE y MERGE con SQL.
Varios motores Cada motor puede interpretar distinto la carpeta. Spark e Impala leen la misma metadata y el mismo estado.
Idea central
Iceberg no reemplaza a Parquet: lo usa para los datos y agrega una capa de metadata que describe con precisión qué archivos forman la tabla en cada momento.

Paso 3 · Autenticarte con Kerberos

  • Kerberos te entrega un ticket temporal que demuestra quién eres ante Spark, HDFS, Hive Metastore e Impala.
  • Sin un ticket vigente, la plataforma te rechaza aunque estés conectado al gateway.
  • El ticket se pide con kinit y se revisa con klist. Dura varias horas; cuando vence, repite kinit.
  1. Escribe klist para ver si ya tienes ticket.
  2. Si responde No credentials, escribe kinit <tu_usuario>@<DOMINIO.CORP> e ingresa tu contraseña.
  3. Vuelve a ejecutar klist: debe mostrar tu usuario y la fecha de vencimiento. 
# 1. ¿Tengo ticket?
[user_penoles@gateway ~]$ klist
klist: No credentials cache found

# 2. Pedir el ticket (contraseña corporativa)
[user_penoles@gateway ~]$ kinit user_penoles@<DOMINIO.CORP>
Password for user_penoles@<DOMINIO.CORP>: ••••••••

# 3. Verificar
[user_penoles@gateway ~]$ klist

10/12/2026 09:01:00  10/12/2026 19:01:00  krbtgt/<DOMINIO.CORP>

Paso 4 · Revisar tu carpeta en HDFS

  • HDFS es el sistema de archivos del clúster. Cada usuario tiene una carpeta personal: /user/<tu_usuario>.
  • Los comandos de HDFS empiezan con hdfs dfs y se parecen a los de Linux: -ls (listar), -mkdir (crear carpeta), -du (tamaño).
  1. Lista tu carpeta personal: hdfs dfs -ls /user/<tu_usuario>.
  2. Si responde sin error (aunque esté vacía), tu ticket y tus permisos funcionan.
  3. Crea una carpeta para notas del laboratorio: hdfs dfs -mkdir -p /user/<tu_usuario>/iceberg_od.
  4. Vuelve a listar y confirma que aparece iceberg_od.

Paso 5 · Abrir Spark con Iceberg habilitado

  1. En el gateway, copia el comando de la derecha completo (las barras \ unen las líneas) y presiona Enter.
  2. Espera unos segundos: Spark pide recursos a YARN y muestra su logo con la versión.
  3. Cuando veas >>>, la consola de Python con Spark está lista. Ya existe una variable spark.
  4. Para salir al terminar: exit() o Ctrl + D.
Configuración Qué hace
spark.sql.extensions Agrega a Spark los comandos de Iceberg: MERGE, CALL, cambios de partición.
spark_catalog = SparkSessionCatalog Permite que el catálogo de la sesión maneje tablas Iceberg y tablas normales.
type=hive Usa el Hive Metastore como catálogo de Iceberg.

  --conf spark.sql.catalog.spark_catalog.type=hive \
  --master yarn --num-executors 2 --executor-cores 2 --executor-memory 2g --driver-memory 2g

Iceberg en palabras simples

  • Apache Iceberg es un formato de tabla abierto: una especificación que define cómo describir, con archivos de metadata, qué datos forman una tabla.
  • No es un motor (no ejecuta consultas) y no es un formato de archivo (los datos siguen en Parquet).
  • Los motores que entienden Iceberg —en Peñoles, Spark e Impala— leen esa metadata para saber exactamente qué archivos consultar.
  • Cada cambio genera una nueva versión de la tabla, llamada snapshot, que se publica de una sola vez.

Los archivos Parquet son las cajas en la bodega. La metadata de Iceberg es el inventario oficial: dice qué cajas forman parte del stock vigente y cuáles pertenecen a inventarios anteriores.

Las tres capas de una tabla Iceberg

  1. Catálogo (Hive Metastore): guarda el nombre ws_usuario.kpi_planta y un puntero al archivo de metadata vigente.
  2. Archivo de metadata (*.metadata.json): esquema, especificación de particiones, propiedades y lista de snapshots.
  3. Manifest list (snap-*.avro): una por snapshot; enumera los manifests que forman esa versión.
  4. Manifests (*-m0.avro): enumeran archivos de datos con su partición, número de filas y estadísticas por columna (mínimo, máximo, nulos).
  5. Archivos de datos (Parquet): las filas de la tabla.
Concepto
El catálogo no guarda las filas ni la lista de archivos: solo dónde está la metadata vigente. Cambiar ese puntero es lo que publica una nueva versión.

Snapshot: la foto de la tabla en un momento

  • Un snapshot es el estado completo de la tabla después de un cambio: qué archivos de datos la forman.
  • Cada escritura (INSERT, UPDATE, DELETE, MERGE, compactación) crea un snapshot nuevo con un ID numérico y una fecha.
  • Los snapshots reutilizan los archivos que no cambiaron: no se copia la tabla completa en cada versión.
  • Un cambio de esquema o de partición actualiza la metadata pero no crea snapshot: no cambian las filas.
  • Los snapshots antiguos se conservan hasta que se expiran (módulo 11). Mientras existan, permiten time travel.

Ejemplo de historia

Snapshot Operación Archivos vigentes
s1 append · carga inicial A, B, C
s2 append · filas nuevas A, B, C, D
s3 overwrite · corrección en D A, B, C, D′
s4 replace · compactación E (A+B+C+D′)

s2 reutiliza A, B y C de s1. En s3, D′ reemplaza a D. En s4 los datos son los mismos, en menos archivos.

Operaciones
append: agrega archivos · overwrite: reemplaza archivos por cambios de filas · delete: quita archivos completos · replace: reorganiza archivos sin cambiar las filas.

Cómo se escribe: el commit atómico

  1. El motor escribe los archivos de datos nuevos en HDFS. Todavía nadie los ve.
  2. Escribe los manifests y la manifest list que los describen.
  3. Escribe un archivo de metadata nuevo con el snapshot agregado.
  4. Pide al catálogo cambiar el puntero solo si sigue apuntando a la versión de la que partió.
  5. Si el cambio se acepta, el snapshot queda publicado. Si otro escritor se adelantó, Iceberg reintenta o informa el conflicto.
Por qué importa
Un lector siempre ve una versión completa: la anterior o la nueva. Si un proceso falla a mitad de camino, la tabla queda intacta; solo pueden quedar archivos sin referencia que el mantenimiento limpia.

Cómo se lee: pruning con metadata

  1. El motor pregunta al catálogo dónde está la metadata vigente.
  2. Lee el snapshot vigente y su manifest list.

Teoría · Anatomía de un CREATE TABLE Iceberg

  • USING iceberg indica a Spark que la tabla es Iceberg. Sin esa cláusula se crearía una tabla Hive tradicional.
  • PARTITIONED BY (days(fecha)) define una partición oculta: Iceberg calcula el día a partir de la fecha. No existe una columna extra que llenar.

  • 'format-version' = '2' habilita las operaciones a nivel de fila (UPDATE, DELETE, MERGE).
  • Los comentarios (COMMENT) documentan cada columna para quien consulte la tabla después.

Teoría · Cómo cambia una fila si Parquet no se edita

  • Un archivo Parquet no se modifica una vez escrito. Para cambiar una fila, Iceberg escribe archivos nuevos y publica un snapshot que los reemplaza.

Módulo 07 · Evolución del esquema

Teoría · Columnas con identidad propia

  • Iceberg asigna a cada columna un ID numérico que nunca se reutiliza. Los archivos de datos guardan los valores por ID, no por nombre ni por posición.
  • Agregar una columna: recibe un ID nuevo. Los archivos antiguos no la tienen, por eso esas filas muestran NULL.
  • Renombrar: cambia el nombre, el ID sigue igual; los datos ya escritos se siguen leyendo correctamente.
  • Eliminar: el ID deja de usarse. Si luego creas otra columna con el mismo nombre, recibe un ID distinto y no "revive" datos antiguos.
  • Estos cambios solo escriben un archivo de metadata nuevo: no crean snapshot ni reescriben datos.

Módulo 08 · Particiones

Teoría · Particionamiento oculto

  • En tablas tradicionales, la partición es una columna técnica (por ejemplo anio_mes) que hay que llenar y filtrar a mano. Si se filtra por la fecha y no por esa columna, se lee toda la tabla.
  • En Iceberg la partición es una transformación de una columna de negocio: days(fecha). Iceberg la calcula al escribir y la aplica al leer.
  • Tú filtras por fecha; el motor traduce ese filtro a particiones y estadísticas de archivos (pruning).
  • La columna de partición aparece en la metadata como fecha_day, pero no es una columna de la tabla.

fecha = DATE'2024-03-15' Sí · 1 día

fecha >= DATE'2024-12-01' Sí · diciembre
month(fecha) = 3 No · lee todo
CAST(fecha AS STRING) LIKE '2024-03%' No · lee todo

Módulo 10 · MERGE

Teoría · Cómo funciona MERGE

  • MERGE INTO destino USING fuente ON condición compara cada fila de la fuente con la tabla usando una llave (aquí: fecha + planta).
  • WHEN MATCHED THEN UPDATE: la llave existe → se actualiza la fila.
  • WHEN NOT MATCHED THEN INSERT: la llave no existe → se inserta.
  • Todo ocurre en un commit: los lectores ven el estado anterior completo o el nuevo completo.
  • Si se ejecuta dos veces con la misma fuente, el resultado lógico es el mismo: es idempotente. Esto permite reintentar una carga sin riesgo de duplicar. 
MERGE INTO ws_usuario.kpi_planta t
USING correcciones s
ON  t.fecha   = s.fecha
AND t.planta = s.planta
WHEN MATCHED     THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *
Regla de oro: llave única en la fuente
Si dos filas de la fuente coinciden con la misma fila del destino, Spark detiene el MERGE con un error. Valida (o deduplica) la fuente antes de ejecutarlo.
Buena práctica
Usa MERGE en lugar de INSERT cuando una carga pueda repetirse o traer correcciones. INSERT repetido duplica filas; MERGE no.

Módulo 11 · Mantenimiento

Teoría · Prevenir archivos pequeños al escribir

  • Partición adecuada al volumen: es la causa más común de archivos pequeños (lo viste en el Lab 3).
  • Batches de carga razonables: cada commit escribe al menos un archivo por partición tocada. Muchas cargas diminutas generan muchos archivos.
  • Distribución de escritura: con write.distribution-mode = hash cada partición se escribe desde una sola tarea, lo que evita varios archivos por partición.
  • Tamaño objetivo: write.target-file-size-bytes (por defecto 512 MB) define el tamaño al que apuntan las escrituras y la compactación.
Buena práctica
Primero escribe bien, luego mide y, por último, automatiza la corrección periódica. La compactación es un complemento, no un sustituto de un buen diseño.

Teoría · Automatizar el mantenimiento en Cloudera

  • El mantenimiento no tiene que ser una tarea manual de cada usuario: se automatiza con un job de mantenimiento programado que ejecuta los mismos procedimientos CALL que practicarás en los Labs 19 y 20.
