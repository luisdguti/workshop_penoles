Módulo 01 · Conceptos

Datos, tablas y llaves

  • Una tabla organiza datos en filas (cada registro, por ejemplo una orden de trabajo) y columnas (cada atributo: fecha, equipo, estado).
  • El esquema describe las columnas y su tipo: texto, número, fecha.
  • Una llave (clave principal o Primary Key) identifica cada fila sin repetirse, por ejemplo id_ot. Es lo que permite hacer join entre tablas: la orden tiene un id_equipo que apunta a la tabla de equipos.
  • En la plataforma, las tablas se guardan como archivos (CSV, Parquet) y un catálogo recuerda su nombre, sus columnas y dónde están.
Concepto
Si una llave se repite donde no debería, al unir tablas las filas se multiplican y los totales quedan mal. Es la regla más importante del módulo 11.

¿Qué es un proceso ETL?

ETL son las siglas de Extract, Transform, Load: extraer, transformar y cargar.

  1. Extraer: tomar solo los datos necesarios de las fuentes (por ejemplo, las órdenes del último trimestre).
  2. Transformar: limpiar, calcular columnas nuevas, quitar duplicados, unir tablas y resumir.
  3. Cargar: guardar el resultado en una tabla final que otros consultan (reportes, tableros, modelos).
Una analogía
Es como preparar un plato: extraer es elegir los ingredientes justos de la despensa, transformar es lavarlos, cortarlos y cocinarlos por etapas, y cargar es servir el plato listo.

Módulo 02 · Plataforma

¿Qué es un clúster?

  • Un clúster es un grupo de servidores (llamados nodos) que trabajan como si fueran uno solo.
  • Cuando los datos son demasiados para una computadora, se reparten entre los nodos y cada uno procesa su parte al mismo tiempo. Eso es el procesamiento distribuido.
  • Hay nodos master (coordinan) y nodos worker (guardan datos y hacen el cálculo).
  • Tú no te conectas a todos: entras por un nodo de acceso llamado gateway (o edge node) y desde ahí envías tu trabajo al clúster.
Analogía
Un turno de mantenimiento: el jefe de turno (master) reparte órdenes y las cuadrillas (workers) las ejecutan en paralelo. Terminar 100 órdenes con 10 cuadrillas toma mucho menos que con una.

Módulo 03 · Apache Spark

Spark en palabras simples

  • Apache Spark es un motor de código abierto para procesar grandes volúmenes de datos repartiendo el trabajo entre muchos servidores.
  • Es rápido porque mantiene los datos intermedios en memoria en lugar de escribirlos a disco en cada paso.
  • Sirve para leer datos de muchas fuentes, limpiarlos, unirlos, resumirlos y guardarlos como tablas: justamente un proceso ETL.
  • Se puede usar con SQL o con lenguajes de programación (Python, Scala, Java). El motor es el mismo.
  • En Cloudera, Spark comparte el catálogo de tablas con Hive e Impala: lo que Spark guarda, Impala lo puede consultar.

Spark no guarda datos por sí mismo: los lee desde HDFS o desde tablas, los procesa y los escribe de vuelta.

Módulo 03 · Apache Spark

Driver, executors y particiones

  • Cuando abres Spark se crea una aplicación con un driver: el “jefe” que recibe tus instrucciones y arma un plan.
  • El driver reparte el trabajo a los executors: procesos que corren en los nodos worker, como cuadrillas.
  • Los datos se dividen en particiones (trozos). Cada executor procesa varias particiones en paralelo.
  • YARN entrega los recursos (memoria y CPU) para el driver y los executors, y los libera cuando cierras la sesión.
Atención
El driver tiene poca memoria. Nunca traigas una tabla grande completa a tu pantalla: usa show() para ver unas pocas filas.
Buena práctica
Cierra tu sesión de Spark cuando termines (exit()): así liberas recursos para tus compañeros.

Módulo 04 · Hive

Hive y el Metastore

  • Apache Hive permite consultar archivos de HDFS como si fueran tablas de una base de datos, usando SQL (HiveQL).
  • Su pieza central es el Hive Metastore: el catálogo que guarda el nombre de cada base y tabla, sus columnas, su formato y la ruta de sus archivos.
  • Una tabla tiene dos partes: los datos (archivos en HDFS) y los metadatos (su definición en el Metastore).
  • Las tablas se agrupan en bases de datos (por ejemplo, ws_USER), y se nombran base.tabla.
  • Las tablas grandes suelen estar particionadas: separadas en carpetas por un valor, como el mes. Así se lee solo lo necesario.

Una tabla particionada por mes

ws_USER.ordenes_trabajo        <- definición en el Metastore
/user/USER/ws_spark/fuentes/ordenes_trabajo/
├── mes=2026-01/part-00000.parquet   <- datos en HDFS
├── mes=2026-02/part-00000.parquet
└── mes=2026-03/part-00000.parquet

Si consultas WHERE mes = '2026-02', el motor abre solo la carpeta de febrero: esto se llama partition pruning.

Concepto
Spark, Hive e Impala usan el mismo Metastore. Por eso una tabla creada con Spark aparece en Hue y se puede consultar con Impala.

Módulo 05 · Lenguajes

El mismo ejemplo en los cuatro lenguajes

Contar las órdenes de trabajo correctivas por mes:

Spark SQL (desde pyspark) 
spark.sql("""
  SELECT mes, COUNT(*) AS cantidad
  FROM ws_USER.ordenes_trabajo
  WHERE tipo_ot = 'Correctiva'
  GROUP BY mes ORDER BY mes
""").show()
PySpark (Python) 
ot = spark.table("ws_USER.ordenes_trabajo")
(ot.where(F.col("tipo_ot") == "Correctiva")
   .groupBy("mes").count()
   .orderBy("mes").show())
Scala Spark (spark-shell) 
val ot = spark.table("ws_USER.ordenes_trabajo")
ot.where($"tipo_ot" === "Correctiva")
  .groupBy("mes").count()
  .orderBy("mes").show()
Java Spark (programa compilado) 
Dataset<Row> ot = spark.table("ws_USER.ordenes_trabajo");
ot.where(col("tipo_ot").equalTo("Correctiva"))
  .groupBy("mes").count()
  .orderBy("mes").show();
Observa
La lógica es idéntica: filtrar, agrupar, contar y ordenar. Cambia la forma de escribirla, no lo que Spark hace. Elige el lenguaje con el que tu equipo se sienta más cómodo.

Paso 1 · Conectarte al gateway

El gateway es el servidor de entrada al clúster. Te conectas a él con SSH, una conexión segura de texto (consola).

  1. En Windows, abre Terminal o PowerShell (menú Inicio → escribe “PowerShell”) o utiliza MobaXterm o PuTTY. En Linux o Mac, abre la terminal.

  5. Si ves un mensaje de bienvenida y el símbolo $, ya estás dentro.

Módulo 06 · Acceso

Paso 2 · Autenticarte con Kerberos

  • La plataforma usa Kerberos: un sistema que, en lugar de pedir tu contraseña a cada servicio, te entrega un ticket temporal que demuestra quién eres.
  • Sin un ticket vigente, Spark, HDFS y Hive te rechazarán, aunque estés conectado al gateway.
  • El ticket se obtiene con kinit y se revisa con klist. Dura varias horas (normalmente una jornada); cuando vence, repite kinit.
Analogía
Es como la credencial de visita en la portería: la muestras una vez y te permite pasar a las salas autorizadas durante el día.
Aplicación Peñoles
En algunos ambientes el ticket se genera automáticamente al entrar por SSH. Si klist ya muestra un ticket vigente, no necesitas kinit.

¿Qué es un DataFrame?

  • Un DataFrame es una tabla con filas y columnas con nombre, como una hoja de Excel, pero repartida entre los executors del clúster.
  • Cada columna tiene un tipo: string (texto), int / double (números), date (fecha). Al conjunto de columnas y tipos se le llama esquema.
  • Los DataFrames son inmutables: no se modifican; cada paso crea un DataFrame nuevo. Por eso escribimos nuevo = anterior.where(...).
  • Puedes trabajarlos con funciones de Python (select, where, groupBy…) o con SQL, registrándolos como vista temporal.

Módulo 09 · Calcular y unir

Crear columnas y agrupar

  • withColumn("nombre", expresión) agrega una columna calculada (o reemplaza una existente).
  • F.when(cond, valor).otherwise(otro) funciona como un SI() de Excel o un CASE WHEN de SQL.
  • groupBy(...).agg(...) resume por grupos: F.count, F.sum, F.avg, F.min, F.max. Usa alias para nombrar cada resultado.
  • orderBy ordena el resultado; F.desc("col") para descendente.
Como una tabla dinámica
groupBy + agg es el equivalente a una tabla dinámica de Excel: filas = columnas del groupBy, valores = funciones del agg.

Por qué construir el ETL por etapas

Un error común es escribir una sola consulta gigante que lee todo, une todo y calcula todo de una vez.

  • Si falla o tarda, no sabes en qué parte está el problema.
  • Si los totales no cuadran, no puedes saber en qué unión se duplicaron o se perdieron filas.
  • Es difícil de leer, de mantener y de reutilizar.

El framework propone lo contrario: avanzar por etapas, con un resultado intermedio y un control después de cada paso.

Analogía: una planta de proceso
El mineral pasa por trituración, molienda y flotación, con un punto de muestreo entre cada etapa. Si la ley cae, sabes en qué etapa revisar. Un ETL por etapas funciona igual.
✓

Controlable

Cada paso tiene un conteo de filas y un tiempo esperado.

⌕

Diagnosticable

Si algo tarda o falla, se identifica el paso exacto.

⚡

Eficiente

Se lee solo lo necesario y se libera pronto la tabla fuente.

⚙

Mantenible

Cada etapa se entiende y se modifica por separado.

Etapa 3 con Spark: la Tabla Maestra

  • La Tabla Maestra define el universo de filas del resultado. Normalmente es la tabla con más registros o la entidad principal (aquí: las órdenes).
  • Puede ser una tabla In tal cual, o formarse con un INNER JOIN de dos tablas cuando solo sirven los registros presentes en ambas.
  • Con INNER, el resultado nunca puede tener más filas que la tabla menor de la relación: si In_Tabla2 tiene 200 registros con llave única, el resultado da 200 o menos, nunca más.
  • Antes del join, comprueba que la llave sea única en una de las tablas.
  • Su número de filas (BASE_FILAS) se guarda y se controla en cada paso posterior. 
# 1) La llave de join debe ser única en el catálogo (debe dar 0)
in_t2.groupBy("id_equipo").count().where("count > 1").count()

tmp1 = in_t1.join(in_t2, on="id_equipo", how="inner")

# 3) Este número debe mantenerse hasta la Tabla Final
BASE_FILAS = tmp1.count()
print("Tabla Maestra:", BASE_FILAS)                       # 10973

# 4) ¿Qué quedó fuera y por qué? (decisión de negocio)
in_t1.join(in_t2, "id_equipo", "left_anti").groupBy("id_equipo").count().show()

Si un join tarda más de 2 minutos: las cinco causas típicas

Causa Qué ocurre Cómo revisarlo Qué hacer
1 · Small files
(archivos pequeños)		 La tabla está repartida en miles de archivos diminutos; Spark pierde tiempo abriéndolos en vez de procesarlos. Hue → Archivos, o hdfs dfs -count ruta. En Spark: len(df.inputFiles()). Compactar al escribir: coalesce(n) o repartition(n) para archivos de 128 MB a 1 GB.
2 · Mal manejo de particiones Particiones de Spark demasiado grandes o demasiadas; tabla particionada por una columna con miles de valores. df.rdd.getNumPartitions() · Spark UI: tareas que tardan mucho más que las demás. Ajustar spark.sql.shuffle.partitions; reparticionar por la llave; particionar tablas por fecha o mes.
3 · No se usa la partición El filtro no usa la columna de partición (o la transforma), y Spark lee la tabla completa. df.explain(): PartitionFilters vacío. Filtrar directo por la columna de partición: where(F.col("mes").between(...)), no por una columna derivada.
4 · Estadísticas desactualizadas El optimizador no conoce el tamaño real y elige una estrategia de join lenta (por ejemplo, no hace broadcast de la tabla pequeña). DESCRIBE EXTENDED base.tabla (Statistics) o SHOW TABLE STATS en Impala. Spark: ANALYZE TABLE base.tabla COMPUTE STATISTICS · Impala: COMPUTE STATS base.tabla · o indicar F.broadcast(tabla_chica).
5 · Data skew (datos desbalanceados) Una o pocas claves concentran gran parte de los registros. Durante un JOIN, GROUP BY, DISTINCT o repartition, una o pocas particiones reciben mucho más volumen que las demás. La mayoría de tareas terminan rápido, pero unas pocas tardan mucho y pueden consumir mucha memoria o generar spill. Spark UI → Stage → comparar Input Size, Shuffle Read, duración y registros por task. Si unas pocas tasks procesan mucho más que las demás, hay skew. También revisar distribución de la clave con df.groupBy("key").count().orderBy(desc("count")). Activar AQE / skew join cuando aplique; usar broadcast para tablas pequeñas; hacer salting en claves extremadamente frecuentes; cambiar la clave de particionado; filtrar datos antes del join; preagregar antes del shuffle.

def paso(df, nombre, base=None, limite_seg=120):
    ruta = RAIZ + "/tmp/" + nombre
    t0 = time.time()
    df.write.mode("overwrite").parquet(ruta)       # materializa el paso
    seg = round(time.time() - t0, 1)
    out = spark.read.parquet(ruta)
    n = out.count()
    msg = "{:<12} filas={:>7}  tiempo={:>6}s".format(nombre, n, seg)
    if base is not None and n != base:
        msg += "  <<< ALERTA filas (esperado " + str(base) + ")"
    if seg > limite_seg:
        msg += "  <<< ALERTA > 2 min: revisar small files, particiones, filtro de particion y estadisticas"
    print(msg)
    return out

Checklist de buenas prácticas

Acceso y entorno

  • Ticket Kerberos vigente (klist)
  • Trabajar solo en tu carpeta y tu base
  • Cerrar la sesión de Spark al terminar
  • Nada de contraseñas en el código

Extracción y filtros

  • Filtrar por la columna de partición
  • Solo las columnas necesarias
  • Filtros de negocio lo antes posible
  • Anotar el volumen de cada tabla In

Joins por etapas

  • Definir la Tabla Maestra y su número de filas
  • Una tabla por join, con LEFT JOIN
  • Llave única en la tabla que se agrega
  • Relaciones 1:N resumidas antes de unir
  • Cada join ≤ 2 minutos y mismas filas

Resultado

  • Validar conteo, unicidad, totales y nulos
  • Guardar en Parquet, sin small files
  • Particionar tablas grandes por fecha o mes
  • Actualizar metadatos en Impala (INVALIDATE METADATA / REFRESH)
Si un join tarda más de 2 minutos
Revisa en este orden: 1. small files · 2. manejo de particiones · 3. uso del filtro de partición · 4. estadísticas actualizadas. Y si cambió el número de filas, primero busca llaves duplicadas.
